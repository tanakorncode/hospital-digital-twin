## 3. ผล load test (2026-10-17, เครื่องพัฒนา, ฐานข้อมูลทดสอบ)

`ADMIN_USERNAME=… ADMIN_PASSWORD=… node apps/api/scripts/load-test.mjs --sockets 20 --bookings 400 --actions 2000`

| การทดสอบ | ผล |
|---|---|
| จองพร้อมกัน 400 คำขอ จาก 20 การเชื่อมต่อ ลง 10 ช่วง รวม 250 ที่ | 0.67 วินาที · สำเร็จ 250 · เต็ม 150 · **ไม่มีช่วงเกินโควตา (PASS)** · latency p50 588 ms / p95 663 ms (ยิงพร้อมกันทั้งหมด จึงเป็นเวลารอคิวรวม) |
| คำสั่งคิว 2,000 คำสั่ง | 1.21 วินาที (~1,650 คำสั่ง/วินาที) · p50 615 ms / p95 1,156 ms |

โรงพยาบาลขนาด 500–1,000 ผู้ป่วยนอก/วัน มีคำสั่งคิวไม่กี่พันคำสั่งต่อวัน จึงยังห่างขีดจำกัดมาก ข้อจำกัดคือรองรับ API **1 process** (SQLite) — ถ้าต้องการหลายเครื่อง/HA ต้องทำ architecture review แยก (เอกสาร §15.3)
**ต้องรันซ้ำบนเครื่องจริงของโรงพยาบาลก่อนนำร่อง** (ใช้ฐานข้อมูลทดสอบ ห้ามใช้ฐานข้อมูลจริง)

## 4. การเฝ้าระวัง และการสำรอง/กู้ข้อมูล

**เฝ้าระวัง:** `GET /health` → `{ ok, schema, messages: { waiting, failed24h } }` — ตั้ง uptime monitor ให้เตือนเมื่อ `ok` ไม่เป็น true, `failed24h` > 0 หรือ `waiting` เพิ่มขึ้นต่อเนื่อง · ตั้งค่า → การแจ้งเตือน (รายการส่งไม่สำเร็จ) · ตั้งค่า → บันทึกการใช้งาน

**สำรอง:** `docker compose exec api node scripts/backup.mjs` (ระบบทำงานอยู่ได้) ทุกคืนผ่าน cron, เก็บ 14 ชุด แล้ว **คัดลอกออกนอกเครื่อง** (ไฟล์มีข้อมูล HN — เก็บในที่ที่จำกัดสิทธิ์และเข้ารหัส)

**ตรวจ/กู้:**
```bash
docker compose exec api node scripts/restore.mjs data/backups/hospital-YYYY-MM-DD-HH-MM-SS.db      # ตรวจอย่างเดียว
docker compose stop api
docker compose run --rm api node scripts/restore.mjs data/backups/hospital-….db --yes            # กู้ (เก็บไฟล์เดิมไว้ข้าง ๆ)
docker compose start api
```
⏳ โรงพยาบาลกำหนด RPO/RTO (เช่น ยอมเสียข้อมูลได้ไม่เกิน 24 ชม. / กลับมาใช้ได้ภายใน 1 ชม.) — ถ้า RPO ต้องน้อยกว่า 24 ชม. ให้สำรองถี่ขึ้น

## 6. ขั้นตอนเปิดนำร่อง

1. ติดตั้งบนเครื่องของโรงพยาบาล (`docs/DEPLOY.md`), เปลี่ยนรหัสผู้ดูแลระบบ, สร้างบัญชีเจ้าหน้าที่
2. ตั้ง LINE OA + LINE Login + LIFF, ใส่ค่าใน `.env`, **ห้ามเปิด `PATIENT_DEV_LOGIN`**
3. รัน load test และซ้อมกู้ข้อมูลบนเครื่องจริง (ใช้ฐานข้อมูลทดสอบ)
4. ซ้อมกับเจ้าหน้าที่ในโหมดสาธิต 1–2 วัน (`docs/STAFF-GUIDE.md`)
5. ตั้งค่า → ข้อมูลผู้ป่วย → **ผู้ป่วยจริง** ก่อนเปิดบริการวันแรก · เปิดสวิตช์ทีละอย่าง: เชื่อม LINE → จองคิว (คลินิกนำร่อง) → แจ้งเตือน → นัดแพทย์ (ถ้า D2 อนุญาต) → QR นำทาง
6. เฝ้าดู 2 สัปดาห์: `/health`, ข้อความส่งไม่สำเร็จ, คำติชมเจ้าหน้าที่/ผู้ป่วย · เกณฑ์หยุดนำร่อง เช่น จองเกินโควตาแม้ 1 ครั้ง, ข้อมูลผู้ป่วยรั่วแม้ 1 ครั้ง, ระบบล่มเกิน RTO

## 7. แผนย้อนกลับ (rollback) และรับมือเหตุขัดข้อง

| เหตุ | ทำทันที | ตามด้วย |
|---|---|---|
| ฟีเจอร์ใดทำงานผิด | ตั้งค่า → ปิดสวิตช์ของฟีเจอร์นั้น (ข้อมูลเดิมยังอยู่) | ดูบันทึกการใช้งาน แก้แล้วเปิดใหม่ |
| ข้อความ LINE ผิด/ส่งรัว | ปิดสวิตช์ "การแจ้งเตือน" (งานที่ค้างจะไม่ถูกส่ง) | ตรวจรายการในหน้าการแจ้งเตือน |
| คิวจริงมีปัญหาหนัก | ตั้งค่า → ข้อมูลผู้ป่วย → สาธิต · เจ้าหน้าที่กลับไปใช้ระบบคิวเดิม/บัตรคิวกระดาษ | รายการผู้ป่วยจริงของวันยังเก็บไว้ ตรวจแล้วกลับมาโหมดจริง |
| สงสัยข้อมูลรั่ว / บัญชีถูกใช้ผิด | ระงับบัญชีเจ้าหน้าที่ (ตั้งค่า → ผู้ใช้งาน), ยกเลิกการเชื่อม LINE ที่เกี่ยวข้อง (หน้าคิว → เชื่อม LINE) | เก็บหลักฐาน (บันทึกการใช้งาน + ไฟล์ backup), แจ้งผู้รับผิดชอบ PDPA, ประเมินหน้าที่ตามกฎหมาย |
| ฐานข้อมูลเสีย | หยุด API, กู้จาก backup ล่าสุด (§4) | แจ้งเจ้าหน้าที่ว่ารายการหลังเวลาสำรองต้องบันทึกใหม่ |
| แพทย์งดออกตรวจ | ตั้งค่า → นัดแพทย์ → ยกเลิกตารางพร้อมเหตุผล (ผู้ป่วยได้ข้อความ) | นัดใหม่ให้ผู้ป่วย |

การเปลี่ยน schema ของเฟส 2 เป็นแบบ **เพิ่มตารางอย่างเดียว** (migration 1–8) ไม่แก้/ลบตารางเฟส 1 การย้อนเวอร์ชันโปรแกรมจึงทำได้โดยไม่ต้องลบข้อมูล ห้าม rollback ด้วยการลบตาราง
